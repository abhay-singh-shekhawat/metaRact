# Cloudflare Workers deployment handoff

**Status:** the repository is prepared and locally validated for
`@opennextjs/cloudflare` on Cloudflare Workers. Nothing has been pushed,
deployed, or connected to a Cloudflare account.

**Validated with:** Next.js `15.5.28`,
`@opennextjs/cloudflare` `1.20.12`, `wrangler` `4.151.3`, Node `26.5.0`
(local), pnpm `9.12.0`, Windows 11.

> OpenNext prints a warning that it is not fully compatible with Windows.
> Every command below was nevertheless run successfully locally. For repeatable
> CI/deployments, use Linux (Workers Builds) or WSL2 and Node 22/24.

## 1. Architecture summary

| Area | Decision |
| --- | --- |
| Adapter | `@opennextjs/cloudflare` (not vinext, as requested). |
| Worker entry | `.open-next/worker.js`, generated by `pnpm build:worker`. |
| Static assets | `.open-next/assets` served through the `ASSETS` binding. |
| Node.js APIs | `nodejs_compat` enabled; MongoDB, `node:crypto`, and Nodemailer's `node:net`/`node:tls` work in `workerd`. |
| Database | MongoDB Atlas through the native driver, one client per request on Workers. |
| File-store fallback | Local Node development only; disabled on Workers. |
| Image optimization | Disabled (`images.unoptimized: true`); no Cloudflare Images binding or paid product needed. |
| ISR / revalidation / `"use cache"` | None. No R2, Durable Object, queue, KV, or self-reference binding is configured. |
| Middleware | Kept. OpenNext runs the separately bundled middleware handler before the Next server; `/admin` redirects were verified. |
| Email | Gmail SMTP through Nodemailer; a fresh transport is created and closed per send. |
| Rate limiting | Upstash Redis when configured; per-isolate memory fallback otherwise. |
| Admin auth | MongoDB-backed sessions with bcrypt; signed dev-cookie fallback is disabled when MongoDB is configured. |

### Why `NEXT_PRIVATE_MINIMAL_MODE=1`

Next.js 15.5 produces a `pages/` directory in the server build even for an
app-router-only project. OpenNext's request pipeline therefore calls
`getMiddlewareManifest()` on every request. That function dynamically
`require()`s `middleware-manifest.json`, which `workerd` cannot resolve, and
every route returned `500` with:

```text
Dynamic require of "/.next/server/middleware-manifest.json" is not supported
```

`NEXT_PRIVATE_MINIMAL_MODE=1` (set in `wrangler.jsonc`) makes the manifest
lookup return `null` instead. Middleware still runs because OpenNext invokes
the middleware bundle separately, before the Next server. This was verified
with the real Worker preview, including the `/admin` redirect.

Keep this variable until a newer adapter/Next release fixes the manifest
handling, then remove it and re-run the preview smoke tests.

## 4. Environment variables

### Build-time (inlined by `next build`)

Set these in the **build environment** (Workers Builds → Build variables, or
the shell/WSL before `pnpm run deploy`). Changing them requires a rebuild.

| Variable | Required | Secret | Purpose |
| --- | --- | --- | --- |
| `NEXT_PUBLIC_SITE_URL` | **Yes** | No | Canonical HTTPS origin. Used for metadata, sitemap, emails, and the same-origin enquiry check. Set it to `https://your-domain` for production. |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | **Yes** in production | No | Public Turnstile site key; the widget will not render without it. |
| `NEXT_PUBLIC_STUDIO_NAME` | No | No | Overrides the default studio name (`Metaract`). |
| `NEXT_PUBLIC_CONTACT_EMAIL` | Recommended | No | Public contact address shown on the static contact page. |
| `NEXT_PUBLIC_WHATSAPP_URL` | No | No | Optional WhatsApp link. |

> `NEXT_PUBLIC_*` values are normally inlined by `next build`, so keep them in
> the build environment. `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is also read again per
> request on `/start-project`, so the same value can be supplied as a Worker
> runtime variable (or `.dev.vars` in local preview) to change it without a
> rebuild — but set the build variable too: `pnpm check:production-config` fails
> when it is missing, and the build-time value is the fallback.

| --- | --- |

> **Important security note:** OpenNext compiles values from `.env*` files into
> `.open-next/cloudflare/next-env.mjs` at build time. If `.env.local` contains
> server secrets when you run `pnpm run deploy`, those secrets are embedded in the
> Worker bundle (runtime dashboard values still take precedence, but the build
> copy exists). For production:
>
> - Keep `.env.local` out of CI/Workers Builds (it is git-ignored, so a clean
>   checkout does not have it).
> - Put only the `NEXT_PUBLIC_*` build values in **Build variables**.
> - Put server-only values in **runtime Variables and Secrets**.
> - If you must deploy from this machine, temporarily move `.env.local` aside,
>   build with only public build variables, then restore it.

## 6. First deployment (CLI)

Do this only after the repository is reviewed and committed. This document does
not deploy anything.

```bash
# Authenticate (opens a browser)
pnpm exec wrangler login

# Build with production public values and deploy.
# Use a shell that does NOT export production secrets from .env.local.
NEXT_PUBLIC_SITE_URL=https://your-domain.example \
NEXT_PUBLIC_TURNSTILE_SITE_KEY=your-public-site-key \
NEXT_PUBLIC_CONTACT_EMAIL=team@your-domain.example \
pnpm run deploy
```

> **Important:** use `pnpm run deploy`, not `pnpm deploy`. The latter is pnpm's
> built-in workspace-package deploy command and will not run this script.

`pnpm run deploy` is:

```text
opennextjs-cloudflare build && opennextjs-cloudflare deploy -- --keep-vars
```

`--keep-vars` is required because Wrangler otherwise deletes dashboard-managed
variables before applying the ones in `wrangler.jsonc`. The script and upload
commands both pass it.

Before the first deploy, create the runtime variables/secrets in the dashboard
(or with `wrangler secret put`). At minimum:

```bash
pnpm exec wrangler secret put MONGODB_URI
pnpm exec wrangler secret put TURNSTILE_SECRET_KEY
pnpm exec wrangler secret put UPSTASH_REDIS_REST_TOKEN
pnpm exec wrangler secret put GMAIL_APP_PASSWORD
pnpm exec wrangler secret put ADMIN_SESSION_SECRET
```

`wrangler secret put` requires the Worker to exist. For a purely CLI first
deploy, run `pnpm run deploy` once to create the Worker (it may be unhealthy
until configuration is complete), add the secrets/variables, then run it again.
Adding a secret itself rolls out a new Worker version; a rebuild is only needed
when a `NEXT_PUBLIC_*` build-time value changes. If you connected the repository
in the dashboard first, you can set the runtime values before the first build.

Then add the non-secret runtime variables in the dashboard:
`MONGODB_DB_NAME`, `UPSTASH_REDIS_REST_URL`, `GMAIL_USER`, `AGENCY_EMAIL`,
`AGENCY_EMAIL_NAME`, `AGENCY_REPLY_TO`, `AGENCY_NOTIFICATION_EMAIL`,
`AGENCY_BCC_EMAIL`, and `ALLOW_DEV_ADMIN=false`.

Do **not** set `NODE_ENV`, `NEXTJS_ENV`, or `ADMIN_DEV_*` in production.

To upload a new version without making it active:

```bash
pnpm run upload
```

3. Root directory: repository root.

Preview deployments: use a separate Worker name (via `wrangler.jsonc` env or a
dashboard override) and separate Atlas database/user if you want preview data
isolated. At minimum, never let a preview branch write to the production

## 8. MongoDB Atlas setup

1. Create an Atlas cluster (M0 or larger). Atlas is a replica set, so the
   transaction path works.
2. Create a dedicated database user with `readWrite` on
   `digital_services_studio` only. Do not use an admin user.
3. Use a `mongodb+srv://...` connection string with TLS and
   `retryWrites=true&w=majority`. URL-encode special characters in the password.
4. Network access: Workers do not have a fixed egress IP. The practical Atlas
   setting is an IP access list entry for `0.0.0.0/0`, combined with a strong
   unique password and TLS. If your security policy forbids that, put a
   fixed-IP proxy in front of Atlas; Workers have no static egress IP of their
   own.
5. Set `MONGODB_URI` and `MONGODB_DB_NAME` as runtime configuration.
6. Bootstrap the first admin from a trusted machine (not from the Worker):

   ```bash
   MONGODB_URI='mongodb+srv://...' \
   MONGODB_DB_NAME='digital_services_studio' \
   pnpm bootstrap-admin admin@example.com 'a-long-unique-password' owner
   ```

   `ADMIN_BOOTSTRAP_ALLOWED` is not required for this script; it is only a
   guard/logging flag.

### Connection behaviour and capacity

- On Workers, each request creates its own `MongoClient` (and therefore its own
  TCP/TLS connection), because sockets cannot be shared across requests. This
  adds roughly ~300 ms of connection overhead on the first operation of a
  request.
- `maxPoolSize: 1` and `maxIdleTimeMS: 5000` limit per-client resource use.
- Clients are not explicitly closed; this matches Cloudflare's documented
  direct-connection pattern. The isolate reclaims them. Monitor Atlas
  connection counts, especially on M0 (500-connection class).
- For higher traffic or consistently low latency, the supported next step is a
  Durable Object that owns a persistent client (not implemented here). The app
  is a low-traffic marketing/admin site, so this was deliberately left out.
- Index creation is idempotent and runs once per Worker isolate.

## 10. Rollback

```bash
pnpm exec wrangler deployments list
pnpm exec wrangler rollback <deployment-id>
```

Or use **Dashboard → Worker → Deployments → Rollback**. Rollback restores the
Worker code/version; it does **not** undo changes you made to dashboard
variables, secrets, DNS, or Atlas data. If a deployment was bad because of an
environment change, fix the variable and redeploy instead of rolling back.

There are no schema migrations to reverse. Index creation is idempotent. If a
release wrote bad data, restore from an Atlas backup/snapshot.

## 11. Known limitations and follow-ups

1. **Minimal-mode workaround** — `NEXT_PRIVATE_MINIMAL_MODE=1` is an internal
   Next.js flag. Re-test and remove it once the adapter/Next combination fixes
   the middleware-manifest dynamic require. Until then, removing it makes every
   route return `500`.
2. **Per-request MongoDB client** — simple and Workers-safe, but no connection
   reuse. Add a Durable Object only if latency/connection limits become a
   problem.
3. **No database ⇒ no enquiries** — the local JSON file store is intentionally
   disabled on Workers. `MONGODB_URI` is mandatory for the enquiry and admin
   features.
4. **Gmail SMTP is not edge-verified** — `nodejs_compat` supports
   `node:net`/`node:tls`, and the transport lifetime was fixed, but a real send
   from `workerd` must be checked after deploy. If Gmail blocks/fails from
   Cloudflare, switch the sender to an HTTP email API (not implemented).
5. **Images are unoptimized** — originals are served directly. This avoids a
   paid Cloudflare Images dependency. If optimization is wanted later, add the
   `images` binding and remove `images.unoptimized`.
6. **Build-time env baking** — see the security note in section 4. This is the
   most important operational trap when deploying from a developer machine.
7. **Windows / Node 26 warnings** — local validation passed, but OpenNext
   recommends WSL2/Linux. Use `NODE_VERSION=24` (or 22) in Workers Builds.
8. **`sharp` override** — pinned to `0.34.5` because the OpenNext bundler cannot
   handle the native loader in `0.35`; Next still installs it as an optional
   peer even though the Worker serves unoptimized images. Newer pnpm may warn
   that `pnpm.overrides` in `package.json` is ignored; the locked tree already
   contains the pinned version, and the repo's package manager is pnpm 9.12.
9. **Rate limiting fallback** — without Upstash, limits are per isolate. Configure
   Upstash for production.
10. **No ISR/cache bindings** — all marketing pages are static and served from
    the assets binding; admin pages and APIs read MongoDB at request time.

## 12. Security checklist before going live

- [ ] `.env.local`, `.dev.vars`, `.open-next/`, and `.wrangler/` are not tracked
      (`git status` and `git check-ignore`).
- [ ] No credential appears in `git log`, `git grep`, or the final diff.
- [ ] Production secrets exist only in Cloudflare's encrypted variables/secrets.
- [ ] `ADMIN_DEV_EMAIL`, `ADMIN_DEV_PASSWORD`, `ALLOW_DEV_ADMIN`,
      `NEXTJS_ENV`, and `NODE_ENV` are absent/false in production.
- [ ] `NEXT_PUBLIC_SITE_URL` is the final HTTPS origin; sitemap/robots use it.
- [ ] `ADMIN_SESSION_SECRET` is a fresh random value, not the local dev value.
- [ ] The Atlas user is least-privilege and the password is unique.
- [ ] Rotate any secret that was ever shared in chat, logs, a screenshot, or a
      build artifact. Deleting `.open-next/` removes the local copy of the
      compiled env, but it does not rotate the credential.
- [ ] Turnstile production keys are configured and the widget renders.
- [ ] Upstash is configured; verify rate limiting from two clients.
- [ ] Gmail app password is valid and “less secure app”/2FA app-password
      requirements are satisfied.
- [ ] Post-deploy smoke tests in section 9 pass.
